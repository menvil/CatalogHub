## Frozen decisions

### F01 — Canonical Category and hierarchy

Retain `central_categories.id`, `slug`, source/reference `name`, `parent_id`, `position`, and Category Draft/Active/Archived. Slug is a URL key, never stable identity. Names shown to users resolve through translations; source `name` is administrative reference text. Description belongs to `CategoryTranslation`. Do not add Published/Synced/Needs Review to `CentralCategoryStatus`. Show separate schema lifecycle and derived validation issues; no stored quality score or unexplained review counter.

One parent; no multi-parent taxonomy or parent-schema inheritance. Archive is the ordinary removal operation; restoration returns an archived Category to Draft for explicit activation. Activation does not publish a Site. Category archive does not delete Products, assignments or Site selections. Category lifecycle and schema lifecycle are independent; Active does not silently mean Approved. Publication gating remains Site-domain policy.

Phase 19.1 actions validate parent existence, self/descendant-parent and the whole changed ancestry under a transaction. Serialize hierarchy mutations using a shared hierarchy lock (including the root sibling scope), then lock affected sibling sets in deterministic ID order. Reparent compacts old and new sibling orders; reorder submits the complete sibling ID set plus expected revision, rejects stale/missing/foreign IDs, writes contiguous order atomically. A version/revision token is required. Dropdown exclusion alone is insufficient. The CA-018 editing workflow (Phase 19.6) requires a downstream routing-impact preview for slug edits; Phase 19 will rebuild projections but will not invent a redirect system. Phase 19.1 keeps canonical name/slug updates available through the foundation action and temporary legacy form, as required by its implementation scope. It does not implement or claim that later screen preview.

### F02 — Global meaning, local assignment

Confirm the refactor: `AttributeDefinition` is a globally reusable canonical meaning. It owns ID, globally unique stable code, source name, data type, measurement dimension/unit references and options. `screen_size` must be reused across TVs/Monitors/Laptops where meaning, measurement and value semantics agree. Same spelling alone never establishes equivalence.

Introduce `CategoryAttributeAssignment`: stable ID, Category FK, definition FK, nullable category-local Section FK, position, `is_required`, `is_visible`, `is_searchable`, `is_sortable`; unique Category/definition. A composite section/category FK prevents cross-category placement. Null section is valid for Ungrouped assignments and the editor shows an explicit Ungrouped bucket. Assignment owns Product-spec/search/sort behavior. Definition `is_filterable` and `is_comparable` do not exist; derive their read summaries from facets/comparison, never copy them into another authoritative boolean.

Product values continue referencing canonical definition IDs, with membership validated through the Product Category assignment. Imports retain category-specific mappings and must reference an assignment-compatible definition. Category assignment removal is blocked while Product values, reviewed mappings, facets, comparison or SEO variable dependencies exist; an explicit migration/detachment plan is required. Hiding is available without deleting values. Canonical definitions are never duplicated for layout differences. Global edits show affected Categories before Save and invalidate every dependent schema; category context does not imply a private definition edit. No separate global-attribute screen is invented.

### F03 — Local, flat sections

Sections remain Category-local. Keep code as stable machine identity, not a routable slug; name is source/reference text. Phase 19 authoring uses one visible section level. Sections are structurally flat from birth: no parent_id column, self FK or parent/children relationships. Same-Category assignment placement uses a composite FK. No nested legacy rows or flattening workflow exists; do not add nested UX. Section code changes require dependency analysis because exports/projections use it. No global section library, section lifecycle, stored icon or canonical description. Visibility uses existing `is_visible`; collapse in the editor is local presentation state, distinct from public `is_collapsible`. Localized name/description use `AttributeSectionTranslation`.

### F04 — Types and semantics

Normal authoring types: string, text, integer, decimal, boolean, enum, multi_enum. Select/Dropdown→enum; Multiselect→multi_enum; Number requires explicit integer or decimal; short Text→string, long Text→text; Boolean→boolean. The numeric screen-size example must select a real length unit; resolution is not presumed measured simply because the prototype says `px`.

Preserve existing JSON definitions/values and expose their legacy type read-only in these screens; new JSON authoring waits for an end-to-end structured contract. JSON is not silently coerced to text. Reject File type: Media ownership and persistence are separate. No variant configuration/count; where the mockup counts enum choices, label the column Options. Any type/dimension/canonical-unit/code mutation with existing values or semantic dependencies is blocked unless an explicit, validated data migration supplies conversions and rollback. Existing options are an additional guard, not the only one.

### F05 — Option identities and retirement

Retain one code identity plus ID; no new `value`+`slug` pair and no automatic casing/hyphen rewrite of persisted codes. Codes are immutable through ordinary edits once created. Labels localize through `AttributeOptionTranslation`; description lives there too. Referenced options cannot be hard-deleted: references include scalar and multi-enum Product values, normalized draft payloads, mapping outputs, facet values and retained exports/projections. Only provably unreferenced options can be explicitly removed under locks and audited. Hide/retire using `is_visible=false`: unavailable for new selections/import label matching, but existing values remain valid and readable with their historical labels. Readers must resolve hidden options for saved values; current visible-only projection lookup requires correction. No default option: missing facts must remain missing, not be fabricated by a default enum choice.

### F06 — One measurement domain

Reuse `MeasurementDimension`, `MeasurementUnit`, `MarketUnitPreference`, `AttributeDisplayRule`, Unit parser/resolver/converter/formatter and `UnitTranslation`. Replace definition free-text dimension/unit with nullable relational dimension/unit IDs. A measured definition requires both; ordinary unmeasured definitions require neither. Measurement is restricted to integer/decimal. Enforce a composite unit/dimension FK plus domain validation, supported by a unique unit `(id, dimension_id)` key; no incompatible pair can persist. Unit ID is identity; unit codes are stored Product fact vocabulary. Product values retain source/canonical unit snapshots; no automatic re-conversion on schema migration. Canonical edits with display-rule dependencies require an explicit future data migration. Units/display-rules UI CA-027…CA-032 remains later; existing-unit selection in CA-021 is permitted.

### F07 — Schema approval is revision-bound

Retain Draft→Reviewed→Approved→Archived. Add schema revision / reviewed revision / approved revision and approval actor/time metadata to support stale-write and review checks. A meaningful Section, assignment, definition, option, facet, comparison or SEO configuration mutation increments each affected Category's schema revision and returns Reviewed/Approved to Draft, clearing review/approval attribution in the same transaction. Canonical changes fan out to all assignments. No-op writes do not change revision/status/audit. Archived schemas are read-only until an explicit restore-to-Draft action; no silent resurrection. Presentation-only editor collapse/search does not invalidate schema. Translation workflow changes do not reset structural approval, but do invalidate locale projections and translation approval as appropriate. Dangerous semantic changes are blocked even when the schema is Draft if data already depends on them. Review and approval lock the Category/revision and validate the same snapshot; no direct schema-status dropdown writes.

### F08 — Canonical facet configuration

`FacetDefinition` is the sole Category facet authority. Attribute-source facets reference a Category assignment (with canonical definition reached through it); Brand/Rating retain their existing sources without a fabricated assignment. `FacetOption` configures filter choices/ranges and must not duplicate canonical option meaning. No definition-local filter flag exists in the initial schema, and there is no runtime fallback.

Facet labels default to translated Attribute labels; optional localized override belongs to a typed `FacetTranslation` using the shared translation workflow. Existing `label_override` becomes reference/default text. Type/widget uses the existing checkbox/select/range/boolean contract, not an unrestricted widget enum. `Show on Sites` becomes canonical facet visibility, clearly labeled as a default; it does not mutate Site publication. Site-specific presentation stays in `SiteFacetOverride`. Prototype Searchable is facet option-list search presentation, distinct from Product full-text indexing: defer it until a real widget contract exists. Preview requires an explicit authorized Site/Locale, real search documents and freshness/count context, never static fake counts. Site overrides are read-only here. Search filter entries are keyed by stable `FacetDefinition.code`, extracting typed values through the source assignment; Attribute code and Facet code are not assumed equal. Sort/full-text sources remain assignment-owned. Preserve existing public facet query keys unless an explicit URL migration is approved.

### F09 — Minimal coherent comparison

Introduce `CategoryComparisonAttribute` rows unique by Category assignment: assignment FK, position, `is_visible`, `highlight_differences`, priority enum high/medium/low (default medium), optional reference label. No comparison-set catalog is needed. Localized overrides use typed `CategoryComparisonAttributeTranslation` in the shared subsystem; default is the canonical Attribute translation. Priority controls visual emphasis, never secondary ordering; explicit position is the sole order. Show selects display participation; removal removes comparison configuration, not the definition/value.

Projection payloads serialize these rows and canonical typed values; public comparison and admin preview consume the same config. Require 2–4 same-category Products in one Site/Locale. Compare normalized numeric values in a common unit, booleans, exact strings and enum codes; multi-enum uses set equality; missing is distinct from false/zero/empty text. Highlight differences means inequality, never a green winner or inferred higher/lower-is-better rule. Preserve section grouping with group order from the earliest configured row, then explicit row order. Config can include an assigned attribute even if its normal spec display is hidden; projection extraction must support that deliberately. `AttributeDefinition.is_comparable` is absent from the initial schema; missing config means no configured comparison rows, not all specs. Explicit Save replaces the prototype's contradictory autosave claim.

### F10 — Safe SEO metadata templates, no routing templates

CA-025 is a real future template engine, not `CategoryTranslation.seo_title` relabeled. Introduce `CategorySeoTemplate` unique by Category + target (`category_page` or `product_page`) with revision and a whitelisted robots choice. Typed `CategorySeoTemplateTranslation` holds localized title/description template text and shared status/hash/approval metadata; it uses the existing Locale and translation workflow. Schema manage changes template structure/variable bindings/default reference copy and robots; translations manage changes localized copy. Do not create a generic expression or JSON translation system.

Grammar permits literal plain text and `{identifier}` placeholders only; no evaluation, conditionals, loops, method/property traversal, scripts, arbitrary functions, includes, remote fetches or user-supplied HTML. Escaped literal braces use `{{` and `}}`. Compile/validate every Save; reject malformed/unknown variables, excessive length/token counts and removed assignment bindings. Reserved variables are `category_name`, `category_slug`, `product_name`, `product_model`, `product_slug`, `brand`; product-only variables are rejected for category-page templates. Attribute variables such as `{screen_size}` and `{resolution}` resolve only from that Category's assignments and bind to definition/assignment IDs at validation, not mutable display labels. Reject reserved-name collisions; unsupported JSON is never eligible. Codes cannot change behind a bound template.

Use the existing translation fallback order: exact active Locale → ordered same-language active Locale → active default Locale → safe reference/default fallback, with provenance exposed in preview. Templates used publicly must be Approved/current; new schemas' revision tracking prevents obsolete approval being reused. Values are plain text: labels for enums/options, deterministic joined multi-enum labels, localized booleans and Unit formatter output for numeric values. Never parse inserted values as templates. No HTML interpolation; encode once at final HTML/attribute output, strip markup/control characters from plain metadata inputs. Missing values produce empty substitution plus collapsed whitespace and a preview warning; if rendered title/description is empty, use the existing product/category fallback. Punctuation remains literal; no implicit expression cleanup.

Metadata precedence for Products: existing Site/local explicit metadata override → explicit Product translated SEO text → approved Category product-page template → existing Product description/title fallback. Category pages: Site/local override → explicit `CategoryTranslation` SEO text → approved Category category-page template → existing description/name fallback. Preview shows both template output and effective output/provenance so overrides are not concealed. Robots combines template policy with Site/indexability restrictions: a template cannot enable indexing of a hidden/pending entity. Allow only index/noindex × follow/nofollow. Persisted outputs enter `SeoProjectionBuilder`/projections; no request-time independent evaluator.

**URL Template is excluded from Phase 19 persistence and execution.** Replace its editable block with a read-only actual canonical URL from existing Site routing. The engine never changes Product/Category slugs, public paths, canonical links or redirects. Use the existing base-URL resolution and encoded canonical slug path; template values cannot introduce schemes, hosts, traversal, query strings or fragments. URL generation would require a separate routing/redirect/collision/hreflang decision. Category slug editing remains F01 and is not template-driven.

Preview uses an explicitly selected real Product from the Category, selected authorized Site/Locale, actual Brand/values/unit formatting and production evaluator. No-product, missing-variable, stale projection, invalid-template and override states are explicit. Unsaved preview/reset are read-only; Reset loads defaults into the form and requires Save. Character counters measure rendered metadata per preview, with advisory bounds rather than a search-engine guarantee. Engine implementation belongs to 19.14, not 19.0.

### F11 — Aggregated translation workspace, shared ownership

Reuse Category, Section, Attribute, Option and Unit translation models. CA-026 lists Category name/description/static SEO, local Sections, assigned global Attribute labels/help text, global Option labels, localized facet overrides, comparison overrides and SEO template strings. Typed translations added for the new owning entities extend the same subsystem; no universal key/value translation store. Unit copy remains CA-030, read-only context here. No translated Category/Section/Option slug.

Match CA-015: explicit Source→Target active Locale, per-field source/target presentation with RTL/LTR, client-only copy, explicit Save, explicit Approve and Mark Outdated; no GET writes or status dropdown that grants approval. Preserve the shared Missing/MachineTranslated/HumanReviewed/Approved/Outdated enum; prototype Active/Needs Review/Draft/Completed are presentation mappings, not new persisted states. No provider contract exists here; machine suggestions/confidence, translator notes, new SEO Intro and Comparison Headline fields are deferred, not fabricated.

Use Brand's lock/transaction/no-op/audit/cache rules. Normalize identity to entity + `locale_id`; retain code as display snapshot. Lock owner, active Locale and exact row, validate optimistic revision and source hash, save as HumanReviewed, clear previous approval on content/source changes. Explicit Approve requires existing HumanReviewed/current source; actor/time are server-owned. Mark Outdated preserves copy and clears approval. Selected reference Locale is read-only context and must never determine canonical ownership or hash. Global Attribute/Option edits visibly affect all using Categories; no category-local copy is silently created.

Source hashes retain existing per-entity canonical contracts: Category name+slug; Attribute code+name+type; Section code+name; Option code+reference label; Unit code+symbol+name. Description/help text have no canonical source today: reference-locale text is advisory, not a hidden cross-locale dependency. A future authoritative localized-source-copy workflow requires its own decision; this phase must not imply that changing another locale auto-outdates these rows. New facet/comparison hashes include owner identity + reference override; SEO template hashes include target/revision + default reference templates + variable bindings. Bulk workspace counts are derived from actual rows in a declared scope and active Locales, deduplicating global entities; no invented per-field completion percentages.

## Permission freeze

All reads require active actor plus Central panel/page admission and the screen capability; all persisted writes additionally pass `central.mutation.execute` before effects. Central context has null audit Site; selecting a preview Site does not grant Site mutation access. UI hiding is not authorization. Canonical source/reference payloads cannot be smuggled through translation routes. Existing config-backed permissions, Gate/policies and `AuthorizationService` remain authoritative. Future Central preview read policies authorize bounded output with the owning SCH/TR capability and validate an existing non-archived Site, supported active Locale, selected Category and Product membership server-side. They do not require a Central operator to acquire a Site Admin role to inspect canonical configuration. Navigation into a Site workspace still requires its existing Site permission and membership; preview access never authorizes that navigation or Site writes.

| Screen / intent | Required capability | Additional boundary / future negative test |
| --- | --- | --- |
| CA-016 list, CA-017 detail, CA-018 Category create/update/reparent/order/lifecycle | `catalog.categories.manage` | Category capability alone cannot mutate schema or translations; Category-only detail may show bounded read-only summary counts, not protected editor payloads. |
| CA-019…CA-025 schema, Sections, global definition + assignments, options, facets, comparison, SEO configuration | `catalog.schema.manage` | Also Central mutation for writes; access directly without categories permission; tampered Category/assignment/Section/Option IDs fail. |
| CA-026 read/Save/Approve/Mark Outdated including localized config copy | `translations.manage` | Also Central mutation for writes; no Category/schema capability required; cannot edit variable bindings, units or robots. |
| Site-specific public preview | Owning screen permission plus explicit Central preview read policy | Validate Site/Locale/Category/Product context; reject archived/missing/mismatched inputs. No Site mutation capability or workspace admission is inferred; local overrides are read-only. |
| Global attribute/option changes launched from Category | `catalog.schema.manage` | Explicit affected-category review, value guards and transactional fan-out; no broader category permission substitution. |

Current role mapping: Super Admin wildcard; Central Admin has all four permissions; Catalog Editor has categories + Central mutation but **not** schema or translations; Translator has translations + Central mutation and Central access; Site Admin has translations but lacks Central admission; Moderator lacks all three module capabilities. Preserve these role grants unless a separate product decision changes them. The old Filament Category permission blanket must be removed in the foundation phases.

## Required audit registry (future implementation)

Phase 19.1 implements the Category core and Category schema lifecycle/invalidation enum events and action-specific `AuditRecorder` allowlists. Phase 19.2 implements the global Attribute created/updated and Category assignment assigned/configured/moved/unassigned events. Phase 19.3 adds only the implemented backend facet/comparison/options/display events; screen-specific events remain reserved for their owning phases. Root sibling reorder uses the actual hierarchy-scope record as subject (no fictional root Category); other core/schema events use Category. Transactions include domain write, revision/approval invalidation and audit; audit failure rolls all back. Emit no event for rejected/no-op/GET/preview operations. No arbitrary model serialization, Product raw payloads, translated bodies, secrets, hashes or config JSON. Stable IDs are allowed only as relationship identity context alongside safe semantic code/name. Changed field names, old/new scalar configuration and bounded deterministic relationship/order lists are sufficient; large fan-out uses one canonical event plus per-Category schema invalidation events with correlation, not copied payloads.

## Consequences, acceptance and exclusions

Required model/schema refactors are explicit: assignment table and global uniqueness; membership FKs/consumer changes; relational measurements; schema/hierarchy revisions and approval metadata; facet assignment/typed localization; comparison rows/typed localization; SEO template/typed localization; locale-ID translation uniqueness. These are initial schema contracts, not incidental UI work. Facet membership and minimal comparison rows land in 19.3; full comparison presentation/localization and SEO/localization extensions follow in 19.12–19.15. This challenges the old Phase 03 “None planned” statement.

Before any screen starts, 19.1–19.3 must prove lossless Product values/Import mappings, bounded concurrency/approval/audit behavior and converged facet/comparison/projection/search contracts with representative persisted-data fixtures. Screen implementation stays serial; later schema additions for comparison/SEO/localization are explicitly owned by 19.13–19.15. No baselines for unfinished screens are created in 19.0.

Deferred/rejected: Units UI CA-027…CA-032; multi-parent/inherited/nested schema UX; Category hard delete; publication/lifecycle conflation; Channels/Facet Sets/Comparison Sets/Category variant configuration; Category icon/color/code without an owning contract; canonical descriptions; duplicated global attributes; option defaults/second identity; File and new JSON authoring; broad import-category/import-attribute, duplicate-category and export-category workflows (existing schema export is separate); generic versions or analytics/monthly trends; arbitrary widgets/facet option search; localized slugs and URL-template routing; machine translation, confidence/notes/glossary; unsupported comparison headline/SEO intro fields; new shared shell or dashboard redesign. The screen audit records every adaptation and its reason.

# Translation architecture

CatalogHub uses normalized, typed per-entity translation tables around the shared `Locale` and `TranslationStatus` contracts. `BrandTranslation` follows the same pattern as Product, Category, Attribute, Section, Option, and Unit translations; there is no Brand-only locale, status, JSON payload, or second translation engine.

Phase 19.0 freezes the future CA-026 aggregated Category translation workspace in [ADR-0003](adr/0003-categories-schema-ownership.md#f11--aggregated-translation-workspace-shared-ownership). It reuses these typed tables and the mature CA-015 workflow, keeps Attribute/Option copy globally owned, and explicitly adds typed translations only for newly approved facet/comparison/template owners. Typed owners use Locale-ID identity and normal runtime owner locking.

`central_brands.name` and `central_brands.slug` remain the canonical administrative identity. `brand_translations.name` is a localized display-name override. The other localized Brand fields are `tagline`, `short_description`, `description`, `seo_title`, and `seo_description`. Slug, lifecycle status, website URL, country code, and media assignments are language-neutral and remain on their canonical domains.

Each Brand/Locale has at most one row, with `brand_id + locale_id` as its database identity. The denormalized locale code follows the established translation schema and is refreshed from the referenced Locale on save, so renaming a code updates the existing row rather than creating another identity. The row uses the shared status enum and carries the common `source_hash`, `approved_at`, and `approved_by_user_id` metadata. Physical Brand or Locale deletion cascades to prevent orphan translations; deleting an approver only nulls the approval actor.

`TranslationSourceHashService::forBrand()` hashes exactly the normalized canonical `name` and `slug`. This is the authoritative Brand source contract; there is no separate persisted source-Locale row. Website, country, lifecycle status, timestamps, media, internal `CatalogTag` assignments, and derived Product Category coverage do not make translated text stale. Catalog Tags are canonical internal administrative classification labels in Phase 11: they have no translation rows and do not participate in Translation Dashboard, Missing, or Outdated workflows. Saves refresh the BrandTranslation hash and invalidate the shared dashboard cache. The existing `DetectOutdatedTranslationsAction` can compare this hash and mark Brand rows outdated while clearing stale approval attribution; the project does not add a Brand-only observer, job, or background detector.

Brands participate in shared Translation Stats, completeness, Missing, Outdated, status filtering, snapshot translation export, and common approval actions. Required Brand coverage for a locale is the canonical Brand count; approved and outdated are row status counts, while missing is required minus existing rows. CA-015 is the Brand-specific authoring presentation, while reports and CA-012 quality issues link to its selected-locale route. Its selected Source Locale uses another active locale as reference; its BrandTranslation is displayed and available for client-side copy only when present. Missing source rows are shown explicitly and are never created by selection. The reference does not replace the canonical hash contract or persist cross-locale ownership or stale dependencies.

CA-015 locks the canonical Brand and exact Brand/Locale row for deterministic Save, explicit approval, and explicit Mark Outdated mutations. Save never grants approval. Only an existing `HumanReviewed` row with a current source hash can delegate to the common approval Action; the server owns actor/time. Editing approved copy or refreshing changed source context returns the row to `HumanReviewed` and clears attribution. Manual Mark Outdated preserves text and coexists with automatic source-hash detection. Meaningful mutations record minimized, transactional Brand-subject Audit events; recent locale activity is a bounded read of those append-only events rather than a second history store.

Public Brand localization, locale fallback resolution, localized APIs/pages, translated slugs, sitemap/SEO delivery, localized media, machine-translation providers, translation memory/glossaries, and persisted field-level workflow are outside CA-015 Phase 18.5. Storing SEO text does not publish it.

## Phase 19.2/19.3 initial Locale-ID authority

Category, Attribute, Section, Option, Unit and Product translation tables are created with unique owner+locale_id. Typed readers/saves resolve Locale IDs. Locale code remains a denormalized runtime display/reference snapshot, refreshed from the reloaded Locale on save. Owners are locked in the same transaction; no collision repair/state or unique-key swapping remains. Global Attribute/Option translations follow their canonical owner across Category assignments. Section/Unit ownership stays local/domain-specific. Text/status/source_hash/approval actor/time remain part of the shared translation contract. Attribute hashes use relational measurement identity. CA-026 remains deferred.

ProductTranslation saves, approvals, outdated transitions and deletion invalidate only their owning Product projections/search through the shared observer and ProjectionStaleDetector. Text/status no-ops preserve output. Category translations invalidate Category and its Products; shared Attribute/Option/Unit translations fan out through assignments, and Section translations stay Category-local. See [the consumer contract](schema-consumer-convergence.md) and [pre-launch policy](pre-launch-schema-consolidation.md).

# Required Checks And Merge Policy

The `develop` branch accepts changes only through a pull request that is current
with the branch and has all of these exact successful check contexts:

- `Backend quality`
- `Frontend quality`
- `Fresh database (PostgreSQL)`
- `Migrations (MariaDB)`
- `Browser smoke (Playwright)`
- `Visual regression (Chromium)`
- `Dependency audit`

`Backend quality` is the stable aggregate for code style, architecture and
static analysis, foundation/legacy unit tests, feature tests, and the browser
harness contract. The database, browser, visual, frontend, and dependency jobs
remain directly required so an aggregate status cannot hide a skipped lane.

The repository currently has one maintainer, so required approving reviews and
last-push approval are disabled: GitHub does not allow a pull-request author to
approve their own change. All review conversations must still be resolved before
merge. Administrators follow the same strict status checks. Direct pushes, force
pushes, branch deletion, and bypasses are not part of the normal flow.

Visual baseline changes must be inspected explicitly by the maintainer and must
never be generated by CI. An independent review should be requested when another
maintainer is available, but it is not a branch-protection requirement in the
solo-maintainer configuration. Auto-merge is disabled. A maintainer merges
manually only after all review conversations are resolved and all required checks
are green; opening a pull request or receiving the first green job is never an
instruction to merge.

Repository protection is verified against GitHub rather than inferred from this
document:

```bash
gh api repos/menvil/CatalogHub/branches/develop/protection
gh api repos/menvil/CatalogHub --jq '.allow_auto_merge'
```

The first response must report strict required status checks, no required
approving review or last-push approval, conversation resolution, enforced
administrator protection, and disabled force pushes and deletion. The second
command must return `false`.

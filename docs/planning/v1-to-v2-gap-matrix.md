# Roadmap v1 to v2 Gap Matrix

Audit basis: functional code at `c8b485ccd161ddfe40ae43f1a09522b894926c78`,
the CA-001…CA-085 and SA-001…SA-064 local reference inventory, discovery's
numbered Public entries, the authoritative screen registry, and the visual
reference manifest.

The final column states whether the target may appear in production navigation
after its roadmap acceptance gate. It does not describe today's navigation.

## Decision meanings

| Decision | Meaning |
| --- | --- |
| `KEEP` | Current implementation and product shape are aligned; complete normal acceptance evidence. |
| `KEEP_AND_REFIT_UI` | Preserve verified domain behavior and refit navigation/screen composition to the approved reference. |
| `REFACTOR` | The current boundary or interaction model conflicts with the product contract and must change without adding scope. |
| `SPLIT` | Preserve shared domain behavior but separate Central-owned and Site-owned presentation/workflows. |
| `DELETE` | Remove an obsolete implementation only in a later approved implementation MR. |
| `POSTPONE` | Keep out of v2 navigation/delivery until it is mapped to an approved screen or separately approved. |
| `MISSING` | No adequate current implementation or approved definition of the target screen/workflow exists. |

## Overall gap assessment

The implementation gap is not a greenfield rewrite. Most canonical, import,
projection, pricing, and public data mechanics have reusable foundations. The
largest gap is product integration: one coherent admin shell, explicit workspace
and immutable active-Site context, screen-specific composition, representative
admin seed data, and semantic/manual visual acceptance for the approved map.

The Public numeric range is not implementable as a whole from the evidence in
this repository: 70 IDs have no authoritative definition and all known Public
IDs lack committed PNG references. The registry makes that a product-decision
blocker instead of inviting implementation guesses.
